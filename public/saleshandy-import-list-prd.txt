1
Overview & Problem Statement

The Problem
Sales teams evaluating or onboarding to Saleshandy are often migrating from competing platforms (Apollo, Lusha, ZoomInfo) with existing prospect and company lists. Today, they must either:

Manually re-search for these contacts in Lead Finder (wasting time and credits)
Use third-party enrichment tools to supplement their lists (abandoning Saleshandy as a source of truth)
Risk re-purchasing records they already own, since there's no way to exclude already-owned contacts from search
This friction creates a gap between signup and activation, and drives churn as users bounce between platforms.

The Solution
Import New List lets users upload their existing contact and company lists directly into Lead Finder. The platform:

Matches their data against the Saleshandy database
Excludes matched records from future searches to prevent re-purchasing
Saves the list for reuse in Lead Finder search filters
This keeps users in-platform, reduces onboarding friction, and helps establish Saleshandy as the source of truth for their prospect data. Importing and matching a list is entirely free — no credits are charged at any step.

Business Goals
Goal	Delivery Mechanism
1. Reduce onboarding friction	Eliminate re-searching; activate migration users faster
2. Reduce churn	Become the source of truth for their prospect data
3. Drive Pro plan upgrades	Feature is gated to Pro and above (see Section 5)

Auto-Detection Keywords
Status: not yet built. Every "Your CSV Fields" dropdown currently opens on "Select column..." — nothing in the current prototype pre-selects a column for the user. This subsection specifies how it should work: matching a user's own CSV header against each Saleshandy field so the common case (a header that's already an obvious match, like "Email" or "Company Name") is mapped automatically, leaving "Select column..." only for headers that genuinely need a human judgment call.

Matching rules:

Matching is case-insensitive and ignores spacing, underscores, and hyphens — "First_Name", "first-name", and "FIRST NAME" all match "First Name" the same way.
Each CSV header is matched against fields in the same fixed order they're listed in (Section 9's "Default Fields Shown" / Appendix B) — core identity fields are checked first, so a header that could plausibly fit more than one field resolves to whichever field is checked first.
A qualified phrase always wins over a bare generic keyword: a header explicitly named "Person LinkedIn URL" or "Company LinkedIn URL" maps to that specific field and never crosses over to the other record type's LinkedIn field, even though both share the generic "linkedin" keyword — the qualified phrase is checked ahead of the bare keyword for exactly this reason.
A header that doesn't match any keyword list for any field is left unmapped ("Select column...") for the user to map by hand — auto-detection never guesses a field it isn't reasonably confident about.
Every auto-mapped field can still be changed or cleared by the user like any other row (see "Deleting a Row" below) — auto-detection only sets the starting point, it doesn't lock anything in.

Deleting a Row
Every row has a delete icon, including First Name and Last Name — there's no field that hides it. What the icon actually does differs by field:

Field	Delete behavior
First Name, Last Name, Company Name, LinkedIn URL, Company Domain/Website, Work Email	Clears the mapping (resets to "Select column...") — the row itself stays, since these are fixed identity/matching fields that a list always needs a shot at populating
Every other field	Removes the row entirely from the table
For the fields that only clear, delete is a single click with a single effect. For every other field, delete is a two-stage click: the first click clears the mapping (the row stays, now empty); a second click, once it's already empty, removes the row entirely.

"+ Add More"
"+ Add More" no longer opens a field picker to browse the whole catalog — since everything is already listed by default, there's nothing left to search for. Instead, it only appears once the user has actually deleted at least one row, and clicking it shows a small list containing only the field(s) that were deleted, letting the user restore them. A restored field reappears at the bottom of the table (not back in its original position), so the fields the user is actively working with stay together near the top.

Invalid Email Mapping
Both People and Company imports — every record type has its own Email concept (Email for People, Company Email for Companies), and either one can get the wrong column mapped to it. No column mapped to Email at all is not flagged here — that's a legitimate, deliberate choice. For People, it costs the user something concrete (see Section 12's "Prospect Auto-Add Rule": the list still gets created, it just won't auto-populate Prospects); Companies have no Prospects concept, so leaving Company Email unmapped costs nothing at all. Either way, only a column that is mapped to Email but doesn't actually contain email addresses gets flagged — a wrong-column mapping (e.g. Phone mapped to Email by mistake), not ordinary missing data.

10
Screen 3: Review & Import

This single screen shows the matching result — there is no separate processing screen. Matching is the only thing the user waits on, and it's free; nothing on this screen costs credits.

Loading State (Matching)
The screen opens into a loading state — a spinner where the completion checkmark will land, headline "Matching your list" — for as long as real matching takes, then resolves into the completed card. Only that header block (the spinner/checkmark icon and the headline) actually changes between the two states — both render inside a fixed-height slot so nothing else on the screen shifts position when it flips. There is no Cancel action on this screen while matching is running — [X] (top-right) remains the only way out.

Matching Mechanics

Matching (free)
The system checks every uploaded row against the Saleshandy database using the mapped fields. This is the only processing step in the whole wizard — there's no follow-on enrichment or verification step, and no credits are charged at any point in this flow.

Matching Identifiers (backend logic)
The system attempts to identify each row using, in priority order:

Priority	Identifier	Notes
1	LinkedIn URL	Highest confidence; sufficient on its own — even with no First Name/Last Name mapped at all, since the name is backfilled from the matched database record (see Section 14)
2	Work Email	Also sufficient on its own — no First Name/Last Name required. Whether it actually matches depends on whether that specific address has a profile on file in Saleshandy's database, not just whether it's validly formatted: a generic/role address (e.g. info@company.com) or one Saleshandy simply has no record of does not match. When it does match, First/Last Name and Company Domain are all backfilled from the matched record for whatever the CSV didn't supply — same treatment as LinkedIn URL (see Section 14)
3	First Name + Last Name + Company Domain	The fallback when neither LinkedIn URL nor Work Email resolves
This logic runs behind the scenes; the user only sees the resulting Total Records / Matched / Unmatched Fields summary on Screen 3, not a tier-by-tier breakdown.

A row that's missing the identifier at one tier still gets a shot at the next: e.g. a row with a mapped LinkedIn URL column that happens to be blank for that particular row falls through to tier 2 or 3 the same as any row that never had LinkedIn mapped at all. A row is only Not Matched when none of its tiers resolve.

Mixed work/personal addresses in one Work Email column: a CSV column mapped to Work Email can still contain a mix of real work addresses and personal-style ones (e.g. common personal-email domains) row by row. Only the rows whose value is recognizably a work address are used for tier-2 matching; a row whose mapped value is personal-style is treated as if tier 2 didn't resolve for that row, and it falls through to tier 3 (or Not Matched if tier 3 doesn't resolve either) — the column mapping itself isn't flagged as invalid (see Section 9's "Invalid Email Mapping"), since the column overall does contain real emails, just not a usable identifier for every row.

Deduplication
Rows sharing the same LinkedIn URL are deduplicated — but not by silently disappearing. The first occurrence is matched normally; every later occurrence is treated as Unmatched instead. It's included in Total Records and the Unmatched Fields count like any other unmatched row, and it appears in the downloadable Failed Report with "Duplicate profile" as its reason — the same treatment Data Enrichment already uses for its own duplicate rows. Rows with no LinkedIn URL mapped have nothing to dedupe on and are processed normally as separate records, even if they look like duplicates by name or company.

Provenance Tag
Every record that lands in a list via this wizard carries an "Imported" tag — a system tag, not a user-editable one, applied at the point the list is created rather than something the user sets themselves.

Aspect	Behavior
Where it shows	In the record's own Tags column in the Saved list view (the combined table showing every record across a user's Private/Public/Team lists) — not as a badge on the list itself in the Lists sidebar
Scope	Applies to every record in a list created through Import New List — People and Company records alike; a list created via the plain "Create New List" modal (Section 6, Entry Point B) and populated some other way does not get it. Unlike the Prospect Auto-Add Rule below, which only ever applies to People, the Imported tag itself is record-type-agnostic
Purpose	Lets a user tell which records in the combined Saved view arrived via import versus search/save, without needing to check which list each row belongs to
Editability	System-applied — it isn't offered as a tag a user can add or remove by hand the way their own tags are
Prospect Auto-Add Rule
Resolves the open question "Prospect View for Lists Without Emails." Separately from this feature, Lead Finder has a product-wide setting — off by default — that automatically saves a lead as a Prospect the moment real contact info is revealed for it. Imported records aren't a special case, but a Prospect record requires an email, so:

Record has	Auto-added as a Prospect when the setting is on?
A revealed Work Email or Personal Email — sourced from Saleshandy via enrichment/reveal	Yes
A CSV-mapped Email/Work Email/Personal Email value, present on an imported row that hasn't been enriched yet	No. A mapped email shows with an Unverified indicator (see Section 13) rather than a real Saleshandy reveal/enrichment — present, but not "revealed," so it doesn't satisfy this check on its own
None of the above — no contact info has been revealed for this record yet	No
This is the same "has revealed contact info" check that already gates the manual "Save as Prospect" action available on any record in the Saved view — a mapped CSV value doesn't count toward it, only a value that's actually come from Saleshandy. Imported records aren't held to a different standard, they just have two extra reasons (a CSV import can arrive with no email data at all, or with one that hasn't been enriched yet) to land in a "no" row above. Companies are unaffected, since Prospects are a person/contact concept rather than a company one — this rule only ever applies to People imports. A user who leaves Email unmapped entirely isn't warned about this trade-off up front (see Section 9's "Invalid Email Mapping" — that check only ever fires for a column that's mapped but wrong, not for one left unmapped); they only see its effect later, in the Saved tab.

Landing in the "no" row isn't a dead end, though: a record with no email still shows the standard "View Email" reveal action right there in the Saved view — the same affordance any record gets in the New or Total tabs, not a reduced one because it arrived via import. A user can reveal it manually at any point after the list is created; doing so satisfies the "has contact info" check above, so the record becomes eligible for automatic Prospect creation from that point on, even though it wasn't at import time.

Data Validation & Edge Cases

Scenario	Handling
Row's primary identifier is blank for that row (e.g. LinkedIn URL is mapped, but empty in that record), while a fallback identifier (Work Email or Company Domain) is present	Matched using the next available identifier tier (see Section 11) — not treated as invalid just because the top-priority field is empty
Invalid rows — no identifier resolves at any tier (LinkedIn URL, Work Email, and First+Last Name+Company Domain are all blank or unmapped for that row)	Auto-skipped during matching. Listed in the Failed Report with reason "No matching identifier" — there was nothing to even attempt a lookup with
Row has a mapped Work Email (or LinkedIn URL), but that specific value has no profile on file in Saleshandy's database — e.g. a generic/role address like info@company.com, or one Saleshandy simply doesn't recognize	Unmatched, with reason "No matching lead found in database" in the Failed Report — distinct from "No matching identifier," since an identifier was present and attempted, it just didn't resolve to anyone
A column mapped to Work Email contains a mix of real work addresses and personal-style addresses (e.g. common personal-email domains), row by row	Only rows whose value is recognizably a work address are matched on tier 2; a row whose value is personal-style is treated as tier 2 not resolving for that row and falls through to tier 3, or to Unmatched (reason "No matching lead found in database") if tier 3 doesn't resolve either. The column mapping itself is not flagged as invalid — see Section 9's "Invalid Email Mapping," which only fires when a mapped column doesn't contain email data at all
People row matched using LinkedIn URL or Work Email alone — First Name / Last Name were never mapped, or were mapped but blank for that row	Name is not left blank: since Saleshandy's database already has a First Name / Last Name on file for that matched profile, the matched record's name is filled in on the created list from the database, not from the CSV
Duplicate rows (same LinkedIn URL)	The first occurrence is matched normally; every later occurrence counts as Unmatched, not silently dropped — it's included in Total Records and the Unmatched Fields count, and appears in the Failed Report with reason "Duplicate profile" (see Section 11)
Duplicate rows with no LinkedIn URL mapped	Nothing to dedupe on; processed normally as separate records
Match status	Binary: Matched or Not Matched — no confidence scores are shown to the user
A record's field (e.g. Email, Work Email, Phone, or a profile field like Job Title) already holds a value mapped from the original CSV on Screen 2, and the user later runs that field's enrichment/reveal action from the Saved tab, after the list has already been created	The enrichment result overwrites the existing mapped value — Saleshandy's enrichment data is treated as more accurate and current than whatever the CSV originally provided. This only happens post-creation, from a deliberate per-record action the user takes in the Saved tab; nothing is overwritten automatically as part of creating the list on Screen 3
A lead's Work Email or Personal Email was already revealed through Saleshandy before this import, and the same lead is then imported again via CSV	The revealed email is retained — CSV data never overwrites it. Saleshandy-sourced data beats CSV-sourced data regardless of which happened first: this is the same precedence as the row above, just in the opposite order (reveal first, import second, instead of import first, reveal second)
A row's matched identity is a lead that's already sitting in the user's own Saved tab (i.e., already enriched/interacted with before this import)	Matched, not Unmatched — and populated from the data already on file in Saved, not from the fresh CSV row's values. Being in Saved already means the user enriched it before, and that data is treated as more accurate than whatever this CSV import brings for the same lead; carrying two different values for the same lead across Saved and a list would be inconsistent
A row's matched identity already belongs to another list (e.g. it's already in list X)	Still added to the new list. Lists are independent — existing membership in one list never blocks or dedupes a lead out of a different one; the same lead can belong to more than one list at a time
Auto Prospect (the product-wide setting from Section 12's "Prospect Auto-Add Rule") is on, and an imported row's CSV data included a usable email, but the row hasn't been enriched yet	No Prospect entry is created at import time — a CSV-mapped email only ever shows with an Unverified indicator (see Section 13), never a real Saleshandy reveal/enrichment, so it doesn't satisfy the "revealed contact info" check
The user later reveals/enriches that same imported row's email (individually, via "Add to List," or via a header/bulk action)	Now the Prospect Auto-Add Rule fires: a Prospect entry is created, with its email verification status shown as Unverified — the same status a prospect imported into the CRM gets. Coming in via CSV import doesn't skip or shortcut verification, it just delays the check until the data is actually revealed
List Name exactly matches the name of a list the user already has	Blocked live on Map Fields, not at Done — [Next] stays grayed out with an inline error, "A list with this name already exists. Choose a different name.", the moment the name collides (see Section 9's "List Name & Share With"). The user must change the name before advancing past Map Fields at all
An imported row appears in the Total tab or Saved tab and has not yet been enriched	No provenance icon, in either tab. Each field shows independently: a mapped field displays its imported value as-is (Email additionally shows an Unverified indicator); an unmapped field shows its normal reveal action (Reveal Email / Reveal Phone / Reveal Personal Email / Enrich Full Profile). In the Actions column, only "Save to List" is available (and enriches the row as it completes) — "Save as Prospect" and "Add to Sequence" stay grayed out until the row is enriched some other way (see Section 13)
User runs the header/bulk "Add to Sequence" (either tab) over a selection that includes one or more un-enriched imported rows	Unaffected by the per-row Actions-column gating above — each affected row is enriched first, then the action completes, exactly like it already does for any other unrevealed lead swept into the same selection; no separate confirmation step for the enrichment side effect
