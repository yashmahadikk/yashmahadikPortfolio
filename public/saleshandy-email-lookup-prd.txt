Problem statement

Users hold lists where the only reliable field is an email address: event and webinar exports, inbound form fills, decayed CRM exports, client-supplied lists. Saleshandy cannot resolve them today. Lead Finder has no email input, Data Enrichment needs First + Last Name or a LinkedIn URL to find a person, and Sage handles one email at a time and drops the names when given several. Users export to FullEnrich or Apollo and re-import, send without personalisation, or leave the list unused. Competitors now ship reverse email lookup as a named feature at 1 credit per person found.

What we are building

This PRD adds email as an input in two places: an Email filter in the Lead Finder People tab (single input or Bulk Search), and Email as a mappable field in Data Enrichment for People enrichment. The Companies tab and Company enrichment do not get an Email input. Both use the same rule. Each email is first looked up against the emails we already hold on Lead Finder profiles; if one matches, that profile is the result. If not, the address is split into first name, last name, company domain and any trailing number. The people with that name at that domain are ordered by tenure in their current role, and the number picks the position: no number is the longest-tenured, 2 is the second. We look up only our own database, never a vendor.

Goals

Let a user who has only email addresses find the people behind them, and the companies they work at, inside Saleshandy, without exporting to another tool
Reuse the matching that is already in production (Name and Company-domain filters) so the feature is a new input, not a new matching system
Keep the filter identical in behaviour to the other bulk filters, so nothing about loading, limits, results or credits has to be relearned
Make an email-only file enrichable in Data Enrichment
Non-goals

Vendor reverse lookup: emails are looked up only against Saleshandy's own database, never sent to a vendor
Personal-email resolution beyond our own database: a personal-domain address is matched only when we already hold it on a profile; it is not searched by name or sent to a vendor
Any new screen: validation summaries, warnings, progress messages, cancel, per-email grouping and CSV import into Bulk Search are optional follow-ons, not scope
Changes to credits or reveal pricing: reveals and enrichment charge as today; the phone-only reveal question is tracked separately
Sage: routing a pasted list to the Email filter is a follow-on once the filter exists
Targets for the first 60 days after general availability. The events that feed them are listed in Appendix B; none can be back-filled, so they ship with the feature.

A baseline exists today: the count of prospects across workspaces that have an email and no name. That is the size of the problem before launch.

Where the lists come from decides which rule fires most: event exports are mostly work emails; inbound forms are mostly personal; CRM exports are a mix with role addresses in them.

RevOps or data owner	CRM export, 2,000–50,000 rows, emails reliable, names and titles stale	Refresh name, title and company in bulk without leaving Saleshandy

As an SDR, I want to paste my attendee emails into Lead Finder and see the matching people, so I can reveal and sequence the right ones
As an SDR, when an email is a shared name at a company, I want to see every candidate, so I can pick the right one instead of the tool guessing
As a researcher, I want to paste the addresses from an email thread and see who they are, knowing that a company address like info@acme.com returns nothing
As a RevOps owner, I want to map an email column in Data Enrichment with nothing else and get name, title and company back, so I can clean a decayed export
As a RevOps owner, I want rows that could not be matched marked Unmatched with a reason, so I know what to do with them
As any user, I want the Email filter to behave like LinkedIn URLs and the other bulk filters, so I do not have to learn a new flow

Search layer

Every pasted email, and every email-mapped row in Data Enrichment, goes through four layers in order. Each layer runs only if the one before it does not settle the email. The requirements below (6.1–6.4) define each layer in detail; the tradeoffs of each layer are in section 13.

Layer	What it does	Outcome
1. Saleshandy database lookup	Exact match of the email against emails stored on profiles (F19)	Found: the exact profile is shown. Not found: layer 2
2. Name + domain	Name read from the email, matched at that company (F12–F18)	One person: shown. Several: layer 3. None: layer 4
3. Name + domain + tenure at current role	The way the email is framed (number, initial, fragment) plus tenure at current role picks the likely owner (F19a)	One likely profile shown. If it still cannot narrow to one, every candidate is shown (F19b)
4. No match	Nothing found at layers 1–3	No profile is shown
Every pasted value goes through the same steps: is it a valid email; do we already hold it (F19); if not, can a name be read from it (F12–F18); and if several people share that name at the domain, which one the number and tenure point to (F19a–F19c). The answer decides whether the email returns one profile, several candidates, or nothing.

ID	Requirement
F12	The local part is split on ., _ and - into name tokens. Two or more name tokens give first and last name (first and last tokens); one token gives a first name only. A trailing number is kept, not removed, because a number is easy to detect reliably, unlike an initial hidden inside a word.
The number is used only when the name search finds several profiles with the same first name, or the same first name and surname, at that domain. We do not decide who joined first from the number alone. We read each candidate's tenure at current role field (in months) in our database and order them by it, longest first (F19a). The person who has been there longest is likely to have the cleaner, un-numbered address, because they got it first.
Example: if one Yash at Saleshandy has 60 months in their current role and another has 36,
yash@saleshandy.com likely belongs to the 60-month Yash and yash2@saleshandy.com to the 36-month Yash. yash.mahadik@ and yash.mahadik2@ work the same way among the Yash Mahadiks.
When the search finds only one profile, the number is dropped and the search continues with the words as the name (F19c). Digits elsewhere in the local part are dropped.
Risk: this does not work when an earlier holder has left. Their profile is no longer current at that domain, so the remaining people move up, and the number can point to the wrong person. For example, if the 60-month Yash has left,
yash2@ would land on whoever is now second, not on the 36-month Yash who owns it
F13	Name tokens are matched as exact tokens against Name (yash matches Yash, not Yashal). Both orders are tried for two tokens (smith.jane@ matches Jane Smith as the same way in name filter )
F13a	A token that is a single letter is treated as an initial: the start of the other name. In yash.m@saleshandy.com, yash is the first name and m means the surname starts with M, so the candidates are every Yash at Saleshandy whose surname starts with M (Mahadik, Mahajan…). In y.mahadik@saleshandy.com, mahadik is the surname and y means the first name starts with Y (Yash, Yogesh…). Both orders are tried, as in F13. If several people still match, the tenure at current role logic (F19a) is applied to try to match one profile; if it cannot, all of them are shown (F19b)
F14	The domain is matched against Company Domain exactly as the Company Domain filter matches today.
F15	In people email If no name token can be read (role accounts such as info@, sales@, hr@, support@, noreply@; digits only; a single character), the address is counted but returns no match. There is no domain-only fallback: only an address with at least one name token can return people
F16	A one-token local part (yash@) searches first name + domain; the candidates are ordered and picked as in F19a–F19c
F17	A local part with no separator — first name and last name joined (yashmahadik@), initial plus surname (ymahadik@, jsmith@), or first name plus initial (yashm@) — is accepted like any other email. It is first looked up as an exact stored email (F19). If we don't hold it, the whole local part is searched as a first name, the same way yash@ is, because the system cannot tell where an initial or a surname begins. So ymahadik@ searches for people whose first name is "ymahadik" at that domain, which usually returns nothing, the same as typing that string into the Lead Finder Name filter
F18	A personal or non-company domain (Gmail, Yahoo, Hotmail, Outlook, Rediff, Proton, iCloud, GMX, Yandex and the rest) is looked up against our own database only (F19). If the address is stored on a profile, that profile is shown. If it is not, the user gets no result: the name logic does not run for personal domains, because there is no company domain to search. No warning is shown
F19	Every email, work or personal, is first looked up against the emails stored on Lead Finder profiles, after normalisation (F11). Only stored emails marked valid count. If exactly one profile holds the email (for a work email, one currently at that domain), that profile is the result and the name logic does not run, whether or not this user has revealed it. If the only holder of a work email has left the company, the email falls through to the name logic, since the address may have been reused. If several current profiles hold it, F19a picks among them. With no stored match, a work email goes to the name logic and a personal email returns nothing (F18)
F19a	Name logic pick: take everyone currently at the domain whose first name, and last name when the email has one, matches (an initial matches the start of the name, F13a). Order them by the tenure at current role field (in months), longest first, and pick the likely owner from the number: no number is the longest tenure, 2 the second-longest, 3 the third. The filter returns that one profile; Data Enrichment enriches the row with it
F19b	Whenever the logic cannot narrow an email to one profile, no one is picked: two candidates have the same tenure, the number is larger than the number of candidates (which also covers birth years and IDs such as yash.mahadik89@), or an initial still matches several people (F13a). The filter then shows every lead the search found for that email in Lead Finder; Data Enrichment gives the row the several-candidates treatment (E8). This will most likely happen when a user pastes name + domain emails of people with the same or similar names working at one organisation
F19c	With only one candidate, that person is the result whatever the number
F20	A mixed paste produces one result set: exact matches (work and personal), name-logic picks and candidate sets together; role and company addresses, and personal addresses we don't hold, contribute nothing

The Email filter is a new input to an existing search, so most of Saleshandy sees it only as another filtered result. The real impact sits in five places: search load, the change to Data Enrichment mapping, what happens when a result found by email is revealed and turned into a prospect, how filter state is stored, and Sage's awareness of the new filter.

The five that need action before launch

Search load is not comparable to LinkedIn URL. A LinkedIn URL lookup is an exact key match. An email becomes a name match plus a domain match, tried in both name orders (F13), so 2,000 emails can be up to 4,000 name-and-domain clauses joined with OR. The non-functional requirement that response time "should match LinkedIn URL" is optimistic; the load test in stage 1 must measure this path specifically, and the 2,000 limit should be set from the result.
E6b changes behaviour for existing Data Enrichment users. Today, mapping an email column to Company Domain returns company data by accident. After launch those rows go unmatched. Check how many jobs map emails to Company Domain today; if the number is material, auto-suggest the Email field on those columns and mention the change in release notes.
The revealed email may not be the pasted email. For emails we hold, the exact lookup (F19) returns the profile that has that address, so this mostly disappears. For name-logic picks, revealing a person can still return a different address from the one pasted (an alias, an older address, or a namesake's). Auto-prospect and "add to prospects" then create a prospect with our email, not theirs, and if the pasted address already exists as a prospect, the user can end up with two prospects for one person.
Filter state has to hold 2,000 emails. Wherever Lead Finder serialises filters — the page URL, Saved Filters, recent searches, shared links, the Report issue payload — 2,000 addresses may exceed size limits and put customer PII in logs and URLs. Store the list server-side and reference it by ID, the way the LinkedIn URL bulk filter should already do; confirm it does.
Sage must understand the Email filter. Sage reads and edits the applied filters. If a user applies Email and then asks Sage to "narrow these to CEOs", Sage has to keep the Email filter; if its filter schema does not know the new type, it may drop it or error.

Every email goes through the same search layer, one step at a time, and stops at the first step that gives an answer:

Saleshandy database lookup. If the email is stored on a profile, that exact profile is shown (F19). If not, go to step 2.
Name + domain. Search the first name and surname read from the email at that company (F12–F17). If one person matches, show them. If several match, go to step 3.
Name + domain + tenure at current role. Use the way the email is framed (the number, initials, fragments) and each candidate's tenure at current role to pick the likely owner (F12, F13a, F19a).
No single match. If steps 1–3 cannot narrow the email to one person, every lead the search found is shown (F19b). If nothing was found at all, there is no result.
Each step trades something away. The tables below set out what, so the risks are understood before build rather than discovered in support tickets.

1. Database lookup	Exact, fast, cheap (a key match). Name + domain + tenure	Narrows the common same-name case to one profile without new data	If the email is expired or the employee has left, positions shift and the result is likely wrong when several profiles share the name. A number in the email can still point to the wrong profile: it may be a birth year or ID, a second sending mailbox of the same person, a counter that starts at 1 rather than 2, or a reused address. Not every organisation frames emails the same way: one Yash Mahadik may get yash.mahadik2@, another yash.m@, another ymahadik@, so the profile may not be matched at all. Promotions reset tenure at current role, so an early joiner can look recent. Tenure can be missing, approximate or tied. Initials and fragments widen the candidate set, so the pick is less reliable. A confident wrong pick does more harm than showing all candidates	No pick on ties or a number larger than the candidate count; all candidates shown instead (F19b); risk stated in F12
4. No single match	Honest: the user sees every candidate and chooses	The user has to tell namesakes apart and may reveal several people to check, paying credits each time. A long list for one email is noise. "No result" doesn't mean the person doesn't exist, only that we don't hold them	Results look like any other Lead Finder search; the cost of choosing stays with the user
Area	Tradeoff
Trust and support	A high number of reports for the wrong profile is likely, especially after a user reveals the email and finds it isn't theirs. Our data isn't fully reliable (stale roles, missing tenure, wrong stored emails), and the feature surfaces that directly. The standard Report issue options have no "Wrong person", so these reports will arrive as "Returns irrelevant results" and be hard to separate
Picking one versus showing all	Picking one profile is what users want, but every pick can be wrong. Showing all is always honest but makes the user do the work.
Coverage versus precision	Every rule that finds more people (initials, fragments, prefixes, ) also brings in more wrong candidates. Every rule that keeps results clean (exact tokens) misses real owners
No labels on results	The user can't tell whether a row came from an exact database match, a tenure pick or a list of candidates. A tenure guess looks as certain as an exact match
Free search, paid reveal	Searching by email is free, so the user gets name, title and company without spending credits. Competitors charge 1 credit per person found for this. Users who already have the email still pay to reveal it
Data Enrichment	A wrong pick in a file is a wrong row written into the user's data and, where credits apply, a paid wrong answer. It is harder to spot than in the Lead Finder results
Data freshness	Results change as our data changes: the same email can resolve to a different profile after a job change or a tenure update
